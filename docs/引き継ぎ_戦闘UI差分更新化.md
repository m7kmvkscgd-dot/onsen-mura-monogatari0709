## 1. 目的(なぜやるか)

ユーザーがPCとiPhone実機を見比べて発見した事実: **iOSでは戦闘演出全般(敵被弾・味方被弾の揺れ/潰れ、攻撃エフェクト等)の「出だしのフレーム」が描画されず、PCと体感品質が大きく違う**。

原因は個々の演出ではなく描画アーキテクチャにある。このゲームは行動のたびに
`renderBattleScreen()`がカードDOMをinnerHTMLで丸ごと作り直し、**作りたての要素に即座に
アニメーション(CSSクラス/WAAPI)を当てる**。iOS Safari(WebKit)は「挿入したての要素への
即時アニメーション」の序盤フレームを描画しない(詳細は§3)。

過去に個別対処してきた不具合は全部この同じ病気の症状だった:
- 攻撃の踏み込みが再描画でブツ切り → 負のanimation-delayで途中復帰(コミット4ece8b9)
- 撃破リアクションが再描画で切れる → body直下のクローンで再生(playEnemyDefeatReaction)
- 行動キャラのぴょんぴょん再発動 → lastPartyBarActingIdの変化時のみ発火パターン(7ced9f3)
- ポップアップの二重表示 → 負のdelayで巻き戻し再開(renderVfxFor)
- 交代の走り込みが描画されない → 常設ステージ+WAAPI(2026-07-26の死闘、§3参照)

**方針決定(ユーザー明言)**: 「今後も同種のバグが出ることを考えたら、大規模でも一番王道の
方法にすべき。UIやダメージエフェクトは1桁フレーム単位で調整する話なのだから」
→ 対症療法をやめ、**カードDOMを使い回して中身だけ書き換える差分更新方式**へ移行する。

## 2. ゴール

- 戦闘中(および探索/野営)のカードDOMは**エンティティごとに1回だけ生成し、以後使い回す**
- 毎行動の更新は「HPバー幅・MPバー幅・数値/テキスト・状態アイコン・クラス(acting/dead/targetable等)・バッジ」の**書き換えのみ**
- 要素の追加/削除は**編成が実際に変わった時だけ**(ロスト・交代・式神/分身の召喚と消滅・逃走離脱)
- **見た目と挙動は現状と完全に同一**を最初のマイルストーンとする(演出の改良はしない。仕組みの入れ替えだけ)
- 差分化が実機で安定確認できた後、負のdelay系の絆創膏を段階的に撤去して簡素化する(別コミット)

## 3. 前提知識: 2026-07-26に確定したiOS Safariの法則(交代演出の死闘で実証)

実機の画面録画をコマ送り解析して確定させた知見。詳細な経緯はメモリ
`feedback-onsen-party-member-transform-ios-bug` とコミット履歴(dd0a127→769e35c→2b599a2→e6923d1→a4decc1)にある。

1. **作りたてのDOM要素に同じJSタスク内で即アニメーションを当てると、WebKitが初回スタイル解決/画像デコード/合成レイヤー確立/初回コミットを終える前にタイムラインだけが進み、序盤(場合によっては全部)のフレームが画面に乗らない**。onfinishは正時に発火する(=JSからは成功に見える)のが罠
2. 事前デコード+rAF二重待ち+初期transformインライン適用でも救えないケースがあった(実測)
3. **確実な解**: 演出用要素は起動時に1個作って**画面外(left:-2000px)に常駐**させ(display:noneは不可=初回描画からやり直しになる)、使う時だけ実座標へ動かしてWAAPIで animate する。これでモック同等の滑らかさ(合成スレッド駆動、ProMotionで120fps)が出る
4. `<img>`(置換要素)を直接animateしない(divラッパーを動かす)。移動量は%でなく実測px
5. 手動rAF駆動(毎フレームstyle書き換え)は「動くが」60fps上限+メインスレッド競合でカクつく。最終手段以外では使わない
6. コマ送り(src差し替え)エフェクトは**全フレームを起動時にImage.decode()して参照を保持**しないとiOSでコマ落ちする
7. 既実装の見本: battle.jsの`getSwapFxStageSingleton`/`makePortraitFxStage`(交代の常設ステージ)、effects.jsの`warmUpAttackVfxAssets`/`getAttackVfxPool`(攻撃VFXの事前デコード+常駐プール)
8. デバッグ手法: 実機の画面録画をもらい`cv2`でフレーム分解(scratchpadにスクリプト例あり)。「JSの状態は正しいのに見えない」場合は描画系を疑い、ロジックを疑わない

## 4. 対象コードの地図

- **ui.js `renderPartyBar(elId, combatants, actingCharId)`** (~line 1000-1100):
  毎回`bar.innerHTML = ""`で全カード再構築。戦闘(battlePartyBar)/探索(dungeonPartyBar)/
  野営(campPartyBar)の3画面共通。ここが本丸
- **battle.js `renderBattleScreen()`** (~line 175-190): 敵カード列(enemy row)の構築+
  renderPartyBar呼び出し。敵カード側も同様に毎回作り直している(敵カード生成コードは
  renderBattleScreen内かその近辺)
- **effects.js**: `resumeAttackLungeOnCard`(踏み込みの途中復帰=絆創膏)、`renderVfxFor`
  (ポップアップの負のdelay復帰=絆創膏)、`shakeClassFor`(__shakeUntilを見て揺れクラスを
  再付与=絆創膏)、`findVisibleCard`(3画面に同idカードが重複存在する罠への対策。§6-1参照)
- **battle.js 交代演出**: `performVoluntarySwap`/`playSwapRunIn`はカードを
  `#battlePartyBar .party-member[data-id=...]`で引く。差分化後もこのセレクタが生きるようにする
- **CSS**: ui.css `.party-member`系 / battle.css `.enemy-card`系 / animation.cssのヒット
  リアクション(hit-shake/hit-flash/squash)。CSSは原則触らない(クラスの付け外し方だけ変わる)

## 6. 地雷リスト(必ず読む)

1. **3画面重複カードの罠**: #dungeonPartyBar/#battlePartyBar/#campPartyBarに同じキャラの
   カードが同時に存在し、非表示画面の分はrectが0になる。既存の`findVisibleCard`が対策済み。
   差分化で「カードを消さず残す」時間が伸びるため、**素のquerySelectorでカードを引いている
   箇所が他に無いか必ずgrepする**(過去に大事故の実績あり)
2. **CSSアニメの再発火**: 同じクラスを付け直しても再生されない/意図せず再生される問題。
   再発火させたい時は「クラス除去→`void el.offsetWidth`→再付与」の既存パターンを使う。
   差分化でカードが生き続けるため、揺れクラスの付け外しタイミングが今より明示的になる
   (今は再構築が暗黙のリセットになっている)
3. **イベントハンドラ**: 現状は再構築のたびにonclickを張り直している。差分化では初回生成時に
   一度だけ張る形になるが、クロージャが古いキャラ参照を掴まないよう、ハンドラ内では
   data-idから現在のエンティティを引き直すこと(targetable時のpendingAllyPick等)
4. **交代とカードの対応**: 交代はカードの「中身」が別キャラに変わる。差分化では
   「カードをキャラidに紐付けて中身ごと差し替える」か「スロット位置に紐付けて中身を更新」かを
   決める必要がある。演出(playSwapRunIn)がdata-idでカードを引くため、**data-idの更新を
   忘れると走り込みが出なくなる**
5. **party-bar-fiveクラス**(5体以上で縮小表示)や`result-xp-grid-2`など、人数で切り替わる
   コンテナ側のクラスも差分更新の対象に含める
6. **順序が変わるケース**: fieldPartyの並びは交代・式神召喚で変わる。DOM順の並べ替えは
   appendChildの再挿入で対応できるが、再挿入は「作りたて扱い」になる可能性がある(iOSの法則)。
   並び替え直後にそのカードへアニメを当てない設計にするか、並びは維持して中身を入れ替える
   方式を優先する
7. **セーブ互換は考慮不要**(ユーザー恒久ルール)。ただしこれは描画層の話なのでそもそも無関係
8. **バランス・スキル・敵データには一切触れない**(ユーザー担当領域)

## 7. 検証方法

- node vmでのロジック検証は効かない(描画の話)。**必ず本番デプロイ→iPhone実機録画**で確認
- ユーザーに「PCとiPhoneで同じ戦闘操作を録画して」と頼み、届いた動画をcv2でフレーム分解して
  1フレーム目から演出が出ているか比較する(この手法は今回のセッションで確立済み)
- 差分化後の機能デグレ確認チェックリスト: 敵タップ選択/味方タップ選択(回復対象)/かばう表示/
  大技予告の照準マーク+⚠️/ストレス落書きオーバーレイ/瀕死…ではなくロスト表示/HPトレイル/
  ダメージポップ(回復)/吹き出しセリフ/交代ボタンとCD表示/式神カード/変身ポートレート
